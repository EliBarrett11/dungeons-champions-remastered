# Combat Resolution Contract

Status legend: **Established** = directly decided; **Proposed** = recommended implementation; **Illustrative** = example only.

## 1. Established rules

- Champions roll initiative at battle start using d20 plus Initiative Modifier.
- The Champion(s) with the highest initiative total receive the opening bonus Ultimate.
- Basic attacks that are due at the same combat timestamp resolve simultaneously.
- If an attack is committed as part of a simultaneous timestamp, the attacker completes that attack even if another committed attack defeats it at that timestamp.
- Class Resources trigger Ultimates when their target is reached.
- Resource resets to zero immediately when an Ultimate triggers; excess resource is not carried over.
- The opening bonus Ultimate is separate from normal resource-triggered Ultimate activations.
- If multiple Ultimates become ready simultaneously, they enter a priority queue ordered by initiative, highest first.
- Before each queued Ultimate resolves, re-check whether its caster can act and whether its target remains valid.
- Rogue critical range: natural 16–20; critical multiplier proposed at 1.5x.
- Sorcerer natural 1–2 always miss; natural 19–20 are critical only if the attack would otherwise hit; natural 20 always hits and crits. Sorcerer Wild Magic is generated by qualifying critical hits and misses.
- Standard Champions: natural 1 always misses and natural 20 always hits and critically hits.
- The intended battle duration is approximately 20–30 seconds when evenly matched; after 30 seconds, damage should escalate exponentially until a winner is decided. The escalation interval/rate/cap remain unresolved.

## 2. Proposed resolution windows

Use one shared event scheduler. Suggested windows:

1. `pre_action`
2. `action_commit`
3. `attack_roll`
4. `hit_confirmed`
5. `damage_calculation`
6. `damage_application`
7. `post_damage`
8. `resource_update`
9. `defeat_check`
10. `on_defeat`
11. `ultimate_queue`
12. `periodic_tick`
13. `battle_end`

Do not rely on object iteration order or render frame order.

## 3. Simultaneous timestamp algorithm (proposed)

1. Collect every action due at the timestamp.
2. Snapshot the combat state and validate/commit eligible actions.
3. Resolve rolls for all committed actions using the seeded RNG.
4. Calculate each action's damage components independently.
5. Apply simultaneous damage/healing/shields according to the effect timing contract.
6. Aggregate qualifying resource events and apply them atomically.
7. Resolve defeat and survival effects.
8. Resolve on-defeat triggers with recursion protection.
9. Add newly ready Ultimates to the priority queue.
10. Resume scheduled combat time only after required resolution windows complete.

The exact interaction between simultaneous healing and lethal damage still requires a final explicit design decision; do not invent a different rule per ability.

## 4. Ultimate queue algorithm (established intent; implementation details proposed)

- Queue key: descending initiative total.
- Equal initiative: stable deterministic tie-break (recommended stable Champion instance ID, then board slot ID).
- Before resolving each Ultimate, re-check caster state and target validity.
- Resource resets at trigger time, not resolution completion.
- If caster is unable to act before its Ultimate begins resolution, skip it unless an explicit effect says otherwise.
- Target invalidation behavior must be defined by the ability: retarget, resolve without target, or fail.

## 5. Damage calculation (proposed, needs balancing)

- Each damage component has its own type and mitigation path.
- Physical Armor and Magic Resistance use diminishing-return formulas provisionally:
  `damage_after_defense = damage * 100 / (100 + max(0, defense))`
- Do not assume Magic Resistance automatically mitigates every magical damage type unless the ability or final defense rules say so.
- Type-specific resistance, vulnerability, and immunity are separate modifiers.
- Damage-type effects (e.g. Burning from Fire) apply only if explicitly specified by the ability or effect.
- Critical multiplier is applied at a defined stage; current proposal is before defensive mitigation.
- Rounding must be consistent and specified centrally.

## 6. Event recursion and safeguards

- Effects default to not triggering themselves.
- Every trigger specifies whether it is once per event, once per attack, once per target, or repeatable.
- Implement a configurable event-depth limit and per-effect trigger budget.
- Chain effects must have explicit maximum targets and recursion behavior.
- Log rejected/limited triggers for debugging.

## 7. Semantic validation beyond JSON Schema

Validate:
- Every referenced ability/effect/resource/status ID exists.
- Duration values and units are compatible.
- Every persistent effect has a removal/expiration rule or explicit battle persistence.
- Every stackable effect has a stacking mode and cap where needed.
- Every damage effect has a damage type and mitigation policy.
- Every control effect declares resistibility, immunity tags, duration cap, and whether it interrupts actions.
- Every resource effect declares the event scope and trigger frequency.
- No accidental trigger cycles or unbounded copy/reflect/chain loops exist.
- An Ultimate has a resource target unless it is explicitly an opening bonus or special non-resource ability.
- All unknown operations fail validation rather than silently doing nothing.
